Agentic engineering control plane

Agents, under control.

CodexTeam is a local software-delivery operating system for self-hosted specialist agents. It combines contract-bound execution, progressive context, capability isolation, evidence-gated acceptance, and deterministic delivery controls.

01 / System shape

One supervisor. Bounded specialists.

CodexTeam uses a hierarchical supervisor pattern. The Lead delegates work; specialists produce artifacts; deterministic mechanisms verify and seal the outcome.

Control model

Supervisor-led

Workers do not spawn workers, negotiate ownership, or change the project plan. The Lead remains accountable.

05 / Context engineering

Deliver the minimum useful context.

The system prefers exact locators, bounded retrieval, and source provenance over injecting entire repositories, histories, and guidance libraries into every turn.

Layer 01

Progressive disclosure

Phase routing, role guidance, and exact handoff targets prevent cold starts from loading the full operating manual.

  • phase-specific guidance
  • task context targets
  • delta-only feedback

Layer 02

Project context MCP

Read-only structured tools expose task state, attempts, gates, repository matches, memory, and cost hotspots.

  • project-bound schemas
  • source hashes + byte counts
  • role-filtered tool sets

Layer 03

Offline sparse RAG

Local Docs uses SQLite FTS5 and BM25 over approved documentation with exact versions and locators.

  • no network runtime
  • read-only index
  • no vector database

Canonical memory

Reviewed project truth

Decisions, open questions, accepted architecture, and ADRs remain human-readable, versionable, and authoritative.

Advisory memory

Source-backed discoveries

Durable research notes are searchable but must be verified against current source. Runtime transcripts are never promoted automatically.

06 / Evidence-gated delivery

A claim is not acceptance.

CodexTeam separates worker output, contract validity, observed evidence, quality gates, independent judgment, Lead acceptance, and canonical closure.

Worker claim

The specialist reports what it believes it completed.

Valid envelope

The launcher proves the report has the required contract shape.

Named evidence

Artifacts and file changes are present, bounded, and attributable.

Fresh gates

Commands pass against the current configuration and workspace digest.

Independent review

Evaluator roles compare claims with requirements and actual output.

Lead closure

Canonical project state advances only after acceptance-level checks.

A result belongs to an attempt. It does not, by itself, complete a task or prove the product meets its acceptance criteria.

07 / Git governance

The model plans. The executor commits.

Git mutation is isolated behind a two-phase, explicitly authorized transaction that verifies the exact candidate tree before creating one local commit.

  1. Read-only planThe Git Steward classifies exact paths and proposes one coherent local commit.
  2. Lead authorizationBranch, HEAD, plan digest, verification, and approved paths are pinned.
  3. Candidate treeDeterministic code constructs the tree without trusting ambient staging state.
  4. Isolated gateThe Integration Gate runs against the proposed tree in a detached worktree.
  5. Exact stagingOnly authorized literal paths are staged and compared with the tested tree.
  6. One local commitThe committed tree and path set are verified after Git returns.

Privilege boundary

Remote authority withheld.

The protocol stops at one verified local commit. Publication remains a separate operator decision.

No pushNo mergeNo tagNo releaseNo remote PR

09 / Evaluation and self-improvement

Evaluate guidance. Learn from delivery.

CodexTeam uses two separate loops: synthetic skill evaluation before guidance promotion, and evidence-bound retrospectives after verified milestone commits.

Before promotion

Skill evaluator

Tests whether instructions route to the intended workflow and preserve authority. It evaluates guidance, not project completion.

  • Structural skill and projection checks
  • Positive, negative, and authority cases
  • Schema-constrained local Ollama request
  • No tools, filesystem, MCP, cloud profiles, or retries
  • Every selected catalog case must pass

After verified commit

Milestone retrospective

Correlates real attempts, gates, commit-tree evidence, correction loops, failures, and usage. Deterministic rules decide whether a proposal qualifies.

  • Exact task, runtime, repository, and role identity
  • Accepted Integration Gate snapshots
  • Commit tree reconstructed from Git blobs
  • Timeout, guard, tool-loop, and retry signals
  • Raw prompts and process output excluded
  • NO_CHANGE / PROPOSALS_RECORDED / BLOCKED_INSUFFICIENT_EVIDENCE

Authority boundary

Proposed is not approved.

When retrospective analysis is applied, qualified findings are automatically captured in the project backlog as Proposed. Preview mode writes nothing. Only an explicit human decision may approve, reject, or defer proposals. Approval is for planning only: it creates no task, changes no contract or skill, and grants no implementation authority. A retrospective may validly conclude NO_CHANGE.

Strong execution substrate. Clear next frontier.

The system already has substantial execution and assurance machinery. Its next maturity step is stronger machine-enforced authorization and split-root completeness, not simply more agents or more memory.
